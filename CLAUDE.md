# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"Sistema de matrículas - Lapreplus" — a server-rendered Spring Boot 3.5 / Java 21 web app for managing student enrollment at an academy: students (`Alumno`), teachers (`Profesor`), courses (`Curso`), academic terms (`Ciclo`), schedules (`Horario`), enrollments (`Matricula`/`MatriculaDetalle`), and payments (`Pago`). UI text, domain names, and messages are in Spanish.

Lapreplus operates three **niveles** (`model/Nivel.java`: `PRIMARIA`, `SECUNDARIA`, `PREUNIVERSITARIO`) as fully independent branches — separate docentes, alumnos, cursos, and horarios — that happen to share one thing: `Ciclo` (the academic term) is a single shared concept across all three, not per-nivel. See "Niveles" below for the full design; this superseded the original single-línea-de-negocio model where `Areas.TODAS` (Ingenierías/Biomédicas/Sociales) were the only classification that existed.

## Build, run, test

This is a Maven project; use the wrapper (no need for a local Maven install).

```
./mvnw spring-boot:run          # run the app (listens on port 9094)
./mvnw clean package            # build a jar (target/*.jar)
./mvnw test                     # run all tests
./mvnw test -Dtest=ClassName    # run a single test class
./mvnw test -Dtest=ClassName#methodName   # run a single test method
```

On Windows use `mvnw.cmd` instead of `./mvnw` if not running under Git Bash/PowerShell wrapper resolution.

There is essentially one test currently (`ProjectApplicationTests`, a Spring context-load smoke test), so `spring-boot:run` plus manual verification in the browser is the primary way changes get checked. When verifying changes yourself, prefer actually starting the app (e.g. on a spare `PORT`) and driving it with `curl` through a login + the affected routes rather than only running `mvnw compile` — several past regressions were template-only (Thymeleaf expression errors) that `compile` can't catch.

**Database**: requires a running MySQL instance. `src/main/resources/application.yml` reads connection details from environment variables (`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `PORT`, `SHOW_SQL`, `THYMELEAF_CACHE`), each with a local-dev default baked in (`jdbc:mysql://localhost:3306/Academia`, user `root`) so `./mvnw spring-boot:run` works out of the box locally; override the env vars for any other environment. `spring.jpa.hibernate.ddl-auto: update`, so schema evolves automatically from entity changes; there are no migration scripts (no Flyway/Liquibase) — see the `model/` note below for what that means in practice. On first run, `DataInitializer` seeds three roles (`ROLE_ADMIN`, `ROLE_CAJERO`, `ROLE_AUXILIAR`) and three users (`admin`/`admin123`, `cajero`/`cajero123`, `auxiliar`/`auxiliar123`) if they don't already exist.

## Architecture

Classic layered Spring MVC + Thymeleaf app, no REST/JSON API — controllers return view names, forms post back via `@RequestParam`/model-attribute binding.

- `controller/` — `@Controller` classes, one per module (`AlumnoController`, `CursoController`, `MatriculaController`, etc.), each mapped under a plural path (`/alumnos`, `/cursos`, ...). Return Thymeleaf view names like `"alumnos/lista"` / `"alumnos/formulario"`, or `redirect:/...`.
- `service/` + `service/impl/` — interface/implementation split. Business rules and transactional boundaries (`@Transactional`) live in `*ServiceImpl`, not in controllers or repositories.
- `repository/` — Spring Data JPA interfaces. Custom queries (e.g. `findAllConEstudianteYSemestre`, `findByIdConDetalle` in `MatriculaRepository`) fetch aggregate roots with eager joins for detail pages, since entity associations default to `FetchType.LAZY`.
- `model/` — JPA entities. Table/column physical names match the Java class/field names (`alumnos`, `profesores`, `ciclos`, `alumnos.area`, `cursos.profesor_id`, `matriculas.alumno_id`, `matriculas.ciclo_id`, etc.) — the tables were renamed directly against the database (`RENAME TABLE`/`RENAME COLUMN`, preserving data) so that `ddl-auto=update` wouldn't create orphaned duplicate tables, and the `@Table`/`@Column`/`@JoinColumn` annotations were updated to match in the same change. **If you're working against a database that predates this rename** (still has `estudiantes`/`docentes`/`semestres`/`carrera`/`docente_id`/`estudiante_id`/`semestre_id`), it needs the same one-time `RENAME TABLE`/`RENAME COLUMN` treatment before the app will start cleanly — don't just let Hibernate create fresh tables under the new names, that orphans the old data. One remaining bit of drift: `Matricula`'s Java *fields* are still named `estudiante` (type `Alumno`) and `semestre` (type `Ciclo`) rather than `alumno`/`ciclo` — renaming those would touch the JPQL derived-query method names (`findByEstudianteId...`) and every template binding (`m.estudiante`, `m.semestre`), so it was left out of scope; keep that in mind when searching for "alumno" or "ciclo" usage on `Matricula`.
- `dto/` — `*Form` classes used for Bean Validation (`@Valid`) on create/edit forms, separate from the JPA entities.
- `exception/` + `controller/GlobalExceptionHandler.java` — `RecursoNoEncontradoException` and `IllegalArgumentException`/`IllegalStateException` are caught centrally and turned into a redirect back to the current module's list view with a flash error message (`mensajeError`), rather than an error page. `GlobalExceptionHandler.rutaBaseDeModulo` derives the redirect target from the request URI against a hardcoded list of module prefixes — add new modules there too if their controllers should get this fallback behavior.
- `config/SecurityConfig.java` — Spring Security filter chain; authorization is role-based per URL pattern (`hasRole("ADMIN")`, `hasAnyRole("ADMIN", "CAJERO")`), configured per-path rather than per-method/annotation. Check this file when adding new controller endpoints that should be restricted, especially write actions (`/nuevo`, `/guardar`, `/editar/**`, `/eliminar/**`), which are consistently admin/cajero-gated while read (`GET`) endpoints are just `authenticated()`. After login, `defaultSuccessUrl` is `/inicio` (the dashboard), not any single module's list.
- `config/DataInitializer.java` — seeds default roles/users on startup (see above).
- `templates/` — Thymeleaf templates, one directory per module (`alumnos/`, `matriculas/`, ...) each typically with `lista.html` (list) and `formulario.html` (create/edit form), plus shared `layout.html` and `fragments/` (menu, sidebar) via `thymeleaf-layout-dialect`. `matriculas/ficha.html` / `ficha-pdf.html` render an enrollment receipt; the PDF variant is rendered server-side to bytes via `flying-saucer-pdf`'s `ITextRenderer` in `MatriculaController.fichaPdf`.

### Enrollment domain notes

`Matricula` (enrollment) is the most complex aggregate: one `Matricula` per (student, `Ciclo`) has many `MatriculaDetalle` (enrolled courses) and many `Pago` (payments, e.g. matrícula fee + pensión installments). `MatriculaServiceImpl.matricular(...)` is upsert-like: if a `Matricula` already exists for that student+ciclo, it replaces the course details (deleting old `MatriculaDetalle` rows directly via repository + `flush()` before clearing the in-memory collection — required because of the unique constraint on `(matricula_id, curso_id)`) rather than creating a new enrollment record. `MatriculaService.agregarCuota(...)` adds a new `Pago` to an already-existing `Matricula` (e.g. next month's pensión) without touching enrollment/course details.

### Soft delete

`Alumno`/`Profesor`/`Curso`/`Ciclo` use a boolean `eliminado` flag for logical deletion rather than removing rows; check for existing filtering-by-`eliminado` conventions in the corresponding repository/service before adding new queries against those tables.

### Niveles and Áreas

- **`Nivel`** (`model/Nivel.java`): `PRIMARIA` / `SECUNDARIA` / `PREUNIVERSITARIO`, each with a display `etiqueta`. This is the top-level, hard-isolation dimension — see the module-by-module notes below for exactly what's scoped by it.
- **`Areas`** (`model/Areas.java`) holds the *second-level* classification, one list per nivel, via `Areas.paraNivel(Nivel)`: `TODAS` (kept under its historical name — don't rename, it's used all over the Preuniversitario module) = `Ingenierías`/`Biomédicas`/`Sociales`; `PRIMARIA` = `"1° grado"`..`"6° grado"`; `SECUNDARIA` = `"1° grado"`..`"5° grado"`. **Primaria and Secundaria's grado labels are identical strings** (both have "1° grado" etc.) — this is only safe because every query that filters by área/grado *also* filters by `nivel` in the same `WHERE` (never área alone off a raw string). If you add a new área/grado-scoped query, it must take both params or it will silently merge Primaria and Secundaria data.
- Every entity that carries an área/grado string (`Alumno.area`, `Curso.areas`, `BloqueHorario.area`) also carries an explicit `nivel` column now — the área/grado field's *meaning* (área vs. grado) is derived from that nivel, but the column itself keeps its original name (`area`) to avoid touching every getter/setter/JPQL/template.
- **`Profesor.niveles`** is the one exception: a `Set<Nivel>` (`@ElementCollection`, table `profesor_niveles`) rather than a single value, because the same person can teach in more than one nivel (per explicit product decision) — unlike `Alumno`/`Curso`, which each belong to exactly one nivel.
- **`Ciclo` has no nivel field** — it's intentionally shared; one ciclo like "2026-I" spans all three niveles. `BloqueHorario`'s uniqueness is therefore `(ciclo_id, nivel, turno, hora_inicio, area)`, not just `(ciclo_id, turno, hora_inicio, area)` — nivel has to be in that tuple or two niveles' schedules could collide on the same ciclo+turno+hora. **Known leftover**: the *old* 4-column unique constraint (`uk_bloque_ciclo_turno_hora_area`, pre-nivel) is still sitting in the DB on any instance that had `bloques_horario` before this change — `ddl-auto=update` only adds/renames constraints it currently maps, it doesn't drop orphaned ones. Harmless in practice (área and grado string sets never collide across niveles), but if you ever need to actually drop it, that's a manual `ALTER TABLE ... DROP INDEX`, not something Hibernate will do for you.
- **`AreaController`** (`/areas`) — the cursos-to-área/grado assignment admin screen — now starts with a nivel tab row, then the existing área/grado cards + curso checklist, both scoped to that nivel (`CursoService.establecerCursosDeArea(nivel, area, cursoIds)`, `AlumnoService.contarPorArea(nivel)`).
- **Migration for pre-existing data**: `config/NivelBackfillRunner.java` (a `CommandLineRunner`, `@Order(1)`) runs on every startup and assigns `PREUNIVERSITARIO` to any `Alumno`/`Curso`/`BloqueHorario` row with `nivel IS NULL`, and inserts a `PREUNIVERSITARIO` row into `profesor_niveles` for any `Profesor` with zero niveles — all via idempotent `WHERE ... IS NULL` / `WHERE NOT EXISTS` queries, so it's a no-op once everything's migrated. This is the project's only data-migration mechanism (no Flyway/Liquibase, see below) — follow this same pattern (nullable column + startup backfill runner) for any future default-value backfill.
- **Known scope gap**: `resumen.html`'s dashboard (`DashboardServiceImpl`) and `/reportes` (`ReporteServiceImpl`) still only report on Preuniversitario — both explicitly call `alumnoService.contarPorArea(Nivel.PREUNIVERSITARIO)` rather than being nivel-aware. Extending them to Primaria/Secundaria is a clear, not-yet-done next step (they're commented `// Resumen/Reportes todavía solo cubre Preuniversitario`).
- **Known scope gap**: `Configuracion` (matrícula/pensión pricing) is still one global row, not per-nivel — Primaria pricing is almost certainly different from Preuniversitario's in reality, but this wasn't part of the original ask, so it wasn't split. Ask before assuming it should stay that way if you're touching pricing.

## Implemented beyond the original scaffold

The app has grown well past its initial commit. These are already in place — **check here before re-adding them**:

- **Success/error flash messages** on every module (`mensajeExito`/`mensajeError`, rendered once in `layout.html`), plus a dedicated `templates/error/404.html` / `500.html`.
- **Server-side search + pagination** on every list view (`alumnos`, `cursos`, `profesores`, `ciclos`, `matriculas`, `pagos`, `usuarios`), all following the same shape: repository `buscar(q, Pageable)` with a `@Query`/`countQuery` pair, controller `@RequestParam(required=false) String q` + `@PageableDefault`, a `.searchbar` block in the template, and `fragments/paginacion :: paginacion` (or `:: paginacionArea` when an `area` filter also needs to round-trip through the page links). Several services also keep an unpaginated `listarTodos()` — that's not redundant, it feeds pickers embedded in *other* forms (e.g. the course checklist in `matriculas/formulario.html`) which must stay unpaginated.
- **Click-to-select searchable pickers** for single-choice fields with many rows (alumno, ciclo, curso, profesor), replacing plain `<select>` dropdowns — a hidden input holds the real value, and a `.courselist`/`.courserow`-style list of clickable rows is filtered live by a search box, so picking is a single click instead of open-dropdown-then-scroll. Shared JS lives in `static/js/buscador-select.js`.
- **Mobile navigation.** The sidebar becomes a slide-in drawer with a hamburger toggle under ~920px; tables scroll horizontally instead of breaking layout.
- **List/blocks view toggle** on `alumnos`, `cursos`, and `profesores` list pages — a `.view-switch` control (`fragments/vista-switch.html :: switch(grupo)`) flips between the classic `<table>` (`data-view-panel="list"`) and a `.entity-grid` of `.entity-card`s (`data-view-panel="grid"`), both scoped by `data-view-group="<grupo>"`. `static/js/vista-toggle.js` wires the toggle and remembers the chosen view per module in `localStorage` (`vista:<grupo>`). When adding a card view for a new module, give every row action from the table a matching button in `.entity-card-foot` — don't drop actions in the card view (bit us once on `alumnos`: the card view was missing "Carnet" that the table had).
- **Layered nivel → área picker for Cursos** — the reference pattern for nivel-scoped "layered" navigation, reach for it before inventing a new one. `/cursos` with no `nivel`/`q` shows `cursos/niveles.html` (Semantic UI `ui cards`, one per `Nivel`, counts via `CursoService.contarPorNivel()`) → `/cursos?nivel=X` shows `cursos/areas.html` (one card per `Areas.paraNivel(nivel)` entry, via `CursoService.contarPorArea(nivel)`) → `/cursos?nivel=X&area=Y` is the familiar filtered list/search/pagination view, scoped to just that nivel+área (never mixed). Both `nivel` and `area` are threaded through `nuevo`/`guardar`/`editar`/`eliminar` so save/cancel/delete round-trip back to where you were instead of dropping you back on the picker. `CursoRepository.buscar(q, nivel, area, pageable)` is the query (`LEFT JOIN c.areas ar ... c.nivel = :nivel AND ar = :area`, `DISTINCT` because of the join); a search (`q`) with no `nivel` searches across all niveles, matching how the rest of the app treats "no filter = search everywhere."
- **Reports & export** (`ReporteController`): PDF (flying-saucer) and Excel (Apache POI) for alumnos por ciclo/turno, ingresos por mes, alumnos morosos, and alumnos por área. The `/reportes` dashboard (`reportes/lista.html`) renders a Chart.js chart per section (bar for ciclo/turno, line for ingresos, horizontal bar for top morosos, doughnut for por área) — categorical/doughnut colors are the validated 5-hue sequence `#2563EB, #D97706, #0EA5E9, #DC2626, #6366F1` (checked against the dataviz-skill CVD validator in this order; re-validate before reordering or adding a 6th). Every PDF template also has a "Resumen general" `table.pdf-info` block (totals/averages/min-max) above the detail table plus a `.pdf-total` line at the bottom, using CSS classes already defined in `fragments/pdf.html` (`pdf-section`, `pdf-info`, `pdf-total`) that were unused before. `ReporteController.generarPdf(...)` centrally sets `fechaGeneracion` on the Thymeleaf `Context` — don't set it per-endpoint, and don't remove it, since `fragments/pdf :: encabezado` reads it for the "Generado el dd/MM/yyyy" line.
- **Dashboard chart** on `resumen.html` (not `inicio.html` — `inicio.html` is the plain post-login landing page with quick-access tiles; `resumen.html`/`ResumenController` is the fuller metrics dashboard) via Chart.js (ingresos por mes, `DashboardServiceImpl.resumenInicio()`).
- **Automatic overdue payments**: `scheduler/PagoScheduler` runs daily (`@Scheduled(cron = "0 0 1 * * *")`) and flips unpaid `Pago`s past their `fechaVencimiento` to `VENCIDO` via `PagoService.marcarVencidos()`.
- **Student expediente** (`/alumnos/{id}/expediente`): every `Matricula` for that student, its cursos, and its pagos, plus an inline "+ Agregar cuota" form. The header shows an avatar + summary stat row (matrículas activas, total pagado, saldo pendiente) computed in `AlumnoController.expediente(...)`.
- **Partial payments.** `Pago` has `montoPagado` (nullable column, treat `null` as `ZERO`) and a computed `getSaldo()`; a fourth `estado` value `PARCIAL` sits between `PENDIENTE` and `PAGADO`. Each payment/abono is its own `Abono` row (`model/Abono.java`: monto, fecha, método, `registradoPor`) rather than overwriting `Pago` directly — `PagoService.registrarAbono(...)` is the only way to move money against a `Pago`. Monthly income reporting (`ReporteServiceImpl.ingresosPorMes`) sums `Abono` rows (real cash received), not `Pago.monto` — don't switch that back to summing pagos, it would double- or under-count once partial payments exist.
- **Extra alumno fields**: `dni` (required, 8 digits), `nombrePadre`/`telefonoPadre` (optional). `email` is optional (nullable, still unique when present) — always null-check/`?: '-'` it in templates, and skip the duplicate-check in `AlumnoServiceImpl.guardar()` when blank.
- **Horarios are built from `BloqueHorario` + `Horario`, not one row per curso-time.** `model/BloqueHorario.java` is the aggregate root: one row per (ciclo, nivel, turno, área, horaInicio) — unique-constrained at the DB level (`uk_bloque_ciclo_nivel_turno_hora_area`; see the "known leftover" note above about the pre-nivel constraint) — holding `horaInicio`/`horaFin`/`tipo` (`CLASE` or `RECESO`). `model/Horario.java` is "one curso within a bloque, on a given día" (`bloque` FK, `curso`, `diaSemana`, `aula`), unique on `(bloque_id, dia_semana, curso_id)`, and keeps read-only delegate getters (`getTurno()`, `getHoraInicio()`, `getHoraFin()`, `getCiclo()`, `getArea()`, `getNivel()`) that forward to `bloque.getX()`. `HorarioService.agruparParaGrilla(cicloId, nivel, area)` returns `Map<Turno, List<FilaHorarioDTO>>` — `dto/FilaHorarioDTO.java` wraps a `BloqueHorario` plus its `Map<DiaSemana, List<Horario>>`, with a `cursosDe(dia)` helper — which `/horarios` (`horarios/lista.html`) and the PDF (`horarios/horario-pdf.html`) both render turno-by-turno. `/horarios` requires picking a `Ciclo` (`?cicloId=` — shared across niveles, so this selector doesn't change with nivel) and shows exactly one nivel+área's grid at a time (`?nivel=`, defaulting to `PREUNIVERSITARIO`; `?area=`, defaulting to that nivel's first entry) via two stacked `.area-tab` rows plus a metrics row (`totalBloques`/`totalAsignaciones` from `HorarioController.listar`) — it never mixes niveles or áreas in one grid. `HorarioServiceImpl.asignarCurso` rejects a curso whose `nivel` doesn't match the bloque's nivel (in addition to the pre-existing área check) — this is the enforcement point that keeps a Primaria curso from ending up on a Preuniversitario schedule. The horarios grid and its PDF share the same turno color coding (mañana=amber, tarde=indigo/lav, noche=sky) — keep both in sync if the palette changes. The old "cruce de horario" (time-overlap) validation was removed: it no longer applies, since all cursos in a bloque intentionally share the same time block and there's at most one bloque per ciclo+nivel+turno+área+horaInicio.
- **Alumnos and Profesores get lighter-weight nivel treatment than Cursos** — a deliberate scope choice, not an oversight. `alumnos/lista.html` has a nivel tab row (defaulting to `PREUNIVERSITARIO`) stacked above the existing área/grado tab row, rather than a separate landing page like Cursos — Alumnos is the highest-traffic screen (daily DNI/name lookups), so it keeps instant search instead of gating it behind an extra click; searching with `q` set but no `nivel` still searches every nivel, same as Cursos. `AlumnoController`/`AlumnoService`/`AlumnoRepository.buscar(q, nivel, area, pageable)` follow the same nivel+area filter shape as Cursos. `alumnos/formulario.html`'s nivel `<select>` drives the área/grado `<select>` via inline JS (`areasPorNivel`, a `Map<String, List<String>>` keyed by `Nivel.name()`, inlined from `AlumnoController.areasPorNivelJson()`) rather than a server round-trip. `MatriculaServiceImpl.matricular(...)` derives nivel from the `Alumno` being enrolled (not a separate param) and looks up cursos via `cursoRepository.findByNivelAndArea(alumno.getNivel(), area)` — this is the enforcement point that keeps enrollment from pulling in another nivel's cursos. `Profesor` just gained a `niveles` checkbox group in its formulario and a pills column in its list (`profesores/formulario.html`, `profesores/lista.html`) — no picker/landing page, since a profesor can span niveles and the list was never "all mixed by default" in the way Cursos was.

## Still open

- `Matricula`'s Java field names (`estudiante`, `semestre`) still don't match the `Alumno`/`Ciclo` types they hold — see the `model/` note above.
- `resumen.html`/`ReporteController` dashboards are still Preuniversitario-only; `Configuracion` pricing is still one global row, not per-nivel — see "Niveles and Áreas" above for both.
- The `/areas` admin screen, `alumnos/lista.html`, and `profesores/lista.html` don't have the full Cursos-style nivel→área landing-page treatment (by design — see the "Alumnos and Profesores get lighter-weight nivel treatment" bullet above) — if that ever needs to change, it's a template-only change following the Cursos pattern, not a schema change.
- The old pre-nivel unique constraint on `bloques_horario` (`uk_bloque_ciclo_turno_hora_area`) is an orphaned leftover on any DB that had the table before nivel was added — see the `BloqueHorario` note above.
